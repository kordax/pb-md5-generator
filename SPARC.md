## S. Требования и границы среза

Проект развивается из генератора документации protobuf в самостоятельную систему документации с CMS. Ориентиры пользователя: удобство чтения MkDocs, интерактивные API-примеры Scalar, редактирование, администрирование и подключаемые хранилища уровня Wiki.js. Это требования к будущему результату, а не утверждение, что весь такой функционал уже реализован.

Полная исходная цель сохранена ниже. Рабочие девять этапов помогают выполнять её по порядку; они не заменяют исходные требования.

### Что означает готовность пункта 1

- Файлы, папки, документы и вложения публикуются с защитой ревизий и прав доступа.
- До изменения исходников сохранены необходимые оригиналы, зарезервирована история и записан журнал транзакции.
- После признанного сбоя восстановление выбирает целиком известное старое или целиком установленное новое состояние.
- Неизвестные изменения, чужие файлы, ссылки, история или Git HEAD сохраняются для проверки оператором. Они не удаляются ради успешного старта.
- Неудачная публикация сохраняет черновик и последнюю успешную публикацию. При незавершённом откате операции с контентом блокируются до восстановления.
- Проверены реальные повторные `New(config)`, а не только отдельные функции проверки журнала.
- Пройдены применимые локальные lint, security, unit/race, integration, Node и Docker проверки. Общий порог покрытия остаётся 90%.
- Результат находится в `main`, сохранён на origin, а инструкция передачи соответствует фактическому состоянию.

Ручная проверка неоднозначных данных остаётся предусмотренным исходом. Пункт 1 не обещает автоматическое исправление любой внешней порчи диска, произвольного переписывания служебных файлов или неизвестного Git-коммита.

## A. Архитектура и расположение кода

### Процесс и интерфейсы

CMS работает одним Go-процессом. Runtime собран через именованные модули Uber Fx: аутентификация, контент, оформление и HTTP. Скомпилированные административные ресурсы встроены в бинарник. Для работы готового контейнера отдельный Node-сервер не нужен.

Основные точки входа и модули:

| Область | Где смотреть | Ответственность |
| --- | --- | --- |
| Команды | `cmd/pb-md5-generator`, `internal/app`, `internal/studio/cli.go` | Генерация, проверка, сборка сайта, запуск CMS, создание первого администратора |
| Runtime | `internal/studio/runtime.go`, `config.go` | Fx, время жизни сервисов, HTTP, каталоги данных |
| Аутентификация | `internal/studio/auth` | Пользователи, роли, grants, пароли, сессии, CSRF и origin |
| Контент | `internal/studio/content` | Дерево файлов, ревизии, черновики, история, публикация, Git и восстановление |
| HTTP API | `internal/studio/apiweb` | Авторизация запросов, документы, файлы, публикация, синхронизация |
| Контракт API | `internal/studio/api/openapi.yaml` | Версионированный HTTP-контракт CMS |
| Админка | `internal/studio/web/assets` | Документы, редактор, файлы, публикации, люди, настройки, темы, навигация и хранилища |
| Reader | `internal/studio/reader*.go`, `internal/site` | Чтение документации с проверкой доступа, preview и рендер |
| Модель и импорт | `document`, `engine`, `internal/parser`, `internal/importer` | Синтаксис, protobuf/OpenAPI, нормализация и генерация |
| Контейнеры | `Dockerfile`, Compose, `deploy` | CMS, отдельный static image, health check, архивирование |
| Приёмка Docker | `testdata/docker-cms.test.py` | Полные сценарии через CLI, HTTP, Git и реальные тома |

Вызовы appearance изнутри content `View` / `ReadView` опасны: appearance сам получает доступ к content. Такое вложение может привести к deadlock.

### Три независимых понятия документа

У страницы есть постоянный ID, путь исходника и выходной URL. Перемещение исходника не должно менять ID страницы. Изменение выходного URL не создаёт автоматический redirect. Домашняя страница сохраняет `index.html`.

Ревизия проекта учитывает инвентарь исходников и идентичность хранилища, включая branch/HEAD. Ревизия конкретного черновика защищает его собственное содержимое. Эти проверки нельзя подменять друг другом.

### Постоянные данные

В контейнере данные находятся в `/data`:

| Каталог | Содержимое |
| --- | --- |
| `content/` | Управляемые исходники, вложения, Git working tree при включённом Git |
| `state/auth/` | Закрытое состояние пользователей и сессий |
| `state/content/` | Черновики, локальная история, настройки хранилищ и журналы восстановления |
| `site/` | Текущая скомпилированная документация |
| `ssh/` | Предоставленные оператором SSH identity и проверенные host keys |

Обычные `down` / `up` сохраняют named volume. `down -v` уничтожает данные и не является командой обновления.

### Что уже доступно в базовой CMS

- Вход, управление пользователями, роли administrator/editor/viewer и отдельные ограничения чтения и записи по путям.
- Хеширование паролей, защищённые сессии, CSRF, проверки Host/Origin и ограничения запросов. Минимум пароля по просьбе пользователя снижен до 10 Unicode-символов; максимум 1024 UTF-8 байта сохранён.
- Редактор документов с исходником, preview, черновиками, публикацией, историей, защитой CAS и явным reviewed rebase.
- Совместное сохранение текста и свойств страницы. Новые локальные правки, сделанные во время сохранения, остаются в редакторе.
- Markdown, безопасный HTML, protobuf и OpenAPI. Формат документа выбирается явно.
- Работа с файлами, текстовыми исходниками, вложениями, папками, перемещениями, регистрацией существующего исходника как страницы и восстановлением сохранённых байтов в отдельный черновик.
- Планируемое удаление непустой папки с проверкой полного поддерева, зависимостей, прав и конфликтующих черновиков.
- Git enrollment для локального проекта, ветки, явные commit/push/fetch/pull и обработка конфликтов. До восьми именованных соединений, один источник pull и независимые push-цели.
- Темы, branding, палитры, параметры рендера, навигация и настройки публикации через админку.
- API-примеры с настройкой запроса, cURL и явным выполнением запроса с показом ответа. Секреты не должны попадать в обычный preview или постоянное браузерное хранилище.
- Полный CMS image, отдельная статическая публикация, постоянные тома, offline backup и восстановление в новый том.

Несколько изменений в одном черновике уже поддерживаются. Атомарная публикация нескольких независимо сохранённых черновиков из UI является отдельным будущим пунктом 2.

## P. Протокол публикации и восстановления

### Обычная публикация

Упрощённая последовательность, без деталей каждой проверки:

```text
прочитать принадлежащий автору черновик
проверить CAS черновика, базу проекта, branch/HEAD и актуальные права
собрать отдельный candidate и полностью скомпилировать его сайт
сохранить оригиналы изменяемых исходников
зарезервировать историю и её неизменяемый план
синхронизировать копии и записать durable journal prepared
повторно проверить authority, исходный проект и права
применить известный набор файлов и каталогов
проверить установленное новое дерево
сохранить предыдущий сайт рядом с output и установить candidate site
проверить source/output/history и записать published
выполнить настроенную явную Git-синхронизацию и записать известный receipt
удалить только точно опубликованную версию принадлежащего автору черновика
переместить новые/вытесненные записи истории и проверить результат
удалить только подтверждённые собственные служебные копии и журнал
```

Ошибка до фиксации публикации запускает ограниченный по времени откат. Для него используется отдельный контекст: отмена HTTP-запроса не должна запрещать безопасно закончить восстановление.

### Что проверяется перед откатом

- Сохранились собственные блокировки source/state.
- Backend, branch и HEAD соответствуют записанной authority.
- Source/backup snapshots совпадают с журналом и не содержат неизвестных добавлений.
- Текущее дерево является допустимой смесью известных before/after записей.
- История до `published` находится в точном исходном размещении.
- Каталоги, которые будут удалены при откате, не содержат посторонних или игнорируемых файлов и ссылок.
- Текущий и сохранённый output имеют известное содержимое.

До `published` история не перемещается. Обратный перенос истории для такой фазы не нужен. После `published` разрешено завершать только известные частичные перемещения неизменяемых записей.

### Повторный запуск

```text
если есть журнал:
    строго разобрать формат, пути, версии, actor и пределы
    проверить собственные каталоги и storage authority
    published:
        подтвердить конечные source/output/history
        завершить известную синхронизационную метаинформацию и cleanup
    rolled-back:
        подтвердить точный before и закончить cleanup
    prepared:
        проверить snapshots и фактическое размещение
        если полный after уже установлен:
            подтвердить его и закончить публикацию
        иначе:
            восстановить только распознаваемое состояние before
иначе:
    убрать только собственные заброшенные candidates без оригинальных backup
    неизвестные/старые backup и orphan output оставить для оператора
```

Восстановление выполняется до создания отсутствующих каталогов output/history. Иначе создание пустого каталога могло бы скрыть реальное состояние прерванного переименования.

### Служебные доказательства

- `state/content/publication.json` содержит authority и версии транзакции.
- `.txn-publication-<id>/` содержит candidate, оригинальные копии и SHA-связанный `history-plan.json`.
- Соседний с output каталог `.studio-publication-<output-hash>-<id>/` удерживает предыдущую публикацию в `previous/`; `after/` используется для временного сохранения новой публикации при откате.
- Оригинальные immutable history payload остаются на месте. Завершение двигает только новые или вытесняемые записи.
- Отсутствие всего stage после cleanup может быть допустимым, если конечные source/output/history доказаны полностью. Существующий stage без plan/owner таким состоянием не является.
- Обычная публикация и удаление дерева сохраняют собственные форматы восстановления. Общий scanner истории сохраняет hash/byte/limit semantics старых поколений; политика открытия каталога у обёрток остаётся разной.

Нельзя удалять журнал или backup ради успешного старта. При неизвестном состоянии сначала остановить сервис, сохранить приватную offline-копию полного тома, проверить journal, pending-синхронизацию, snapshots и Git. После подтверждённого точечного ремонта повторный запуск может закончить восстановление. Startup recovery сам не делает commit, push или reset HEAD.

### Исправленные дефекты этого среза

- Ошибка отката обычной публикации могла приводить к удалению единственной копии оригиналов. Копии теперь живут до подтверждённого результата.
- Создание отсутствующего output до recovery могло маскировать прерванную замену сайта.
- После удаления stage, но до удаления журнала, `readSource` мог вернуть обычный `os.ErrNotExist`, а восстановление ожидало только внутренний `ErrNotFound`. Теперь оба случая признаются лишь вместе с проверкой отсутствия stage и полной конечной истории.
- Лишняя запись в `pending.Hashes` не должна приниматься как точный receipt. Проверяется полный состав путей и хешей.
- Полное перекопирование сохранённой истории при каждой публикации заменено immutable delta. Старые payload не переписываются.
- Повторяющееся bounded `ReadDir` / EOF / close-обслуживание сведено в один закрывающий дескриптор primitive; пределы и ownership-проверки остаются у вызывающих функций.

Общий scanner истории введён для согласованной проверки формата и лимитов. Ускорение I/O от самого объединения scanner не заявляется.

### Очистка после успешной проверки

Приёмка обнаружила реальный сбой: если после записи `published` каталог StateDir становится readonly, рекурсивное удаление могло убрать owner/plan и остальные данные stage, но не сам каталог. После возврата прав следующий запуск видел существующий stage без доказательств и останавливался.

`removePublicationTree` теперь сначала атомарно переименовывает полностью проверенный каталог в соседний `.retired-<исходное имя>` через существующий confined `renamePublication`, синхронизирует родительский каталог и только затем удаляет содержимое. Это относится к обычному stage и прежнему output. Собственный provisional stage без журнала и backup удаляется тем же primitive после прежних owner/conflict-проверок. Ошибка rename оставляет исходные доказательства. Ошибка последующего удаления оставляет журнал и отсутствующий canonical path; повторный запуск опирается на полную проверку конечных source/output/history.

Оставшиеся `.retired-*` намеренно сохраняются для ручной проверки оператором. Они могут содержать оригиналы и приватные данные. Не удалять такие каталоги по одному имени и не добавлять безусловный автоматический GC. Если retired destination уже занят, rename отказывает, сохраняя существующие данные. Проверены прерывание между rename и удалением, частично очищенный stage, оба типа коллизий и отказ удаления самого журнала.

Фаза `rolled-back` может быть записана после доказательства точного Before, даже если последующая очистка откажет из-за посторонних private entries. Это допустимый прогресс журнала; исходники, сайт и чужие файлы при отказе остаются на месте.

Версии инструментов задаются репозиторием. Из известных применявшихся версий: Go 1.26.10, golangci-lint 2.12.2, actionlint 1.7.12, govulncheck 1.9.0, gosec 2.30.0, go-test-coverage 2.18.9. Использовать команды текущего Taskfile и CI, не обновлять инструменты попутно.

GitHub Actions не ждать. Проверка выполняется локально. На этой машине есть пользовательский ignored `tmp/main.go`; его не удалять. Финальный прогон выполняется в чистом detached worktree точно зафиксированного candidate, чтобы scratch-файлы не попадали в Go-пакеты. Старый `/tmp/pb-docs-security-ci-xzb5185d` является только временной рабочей площадкой, а не частью продукта.

### Просмотр и запуск

```sh
task docker:up
# Остановка без удаления данных:
task docker:down
```

- Админка: <http://localhost:8080/_docs/admin/>.
- `--build` пересобирает образ, `-d` оставляет контейнер в фоне, `--wait` ждёт health check.
- `task docker:up` пересобирает текущие локальные исходники, запускает CMS и после успешного health check печатает ссылки на документацию и админку. Фактический порт получает через `docker compose port`, включая изменённый `DOCS_PORT`. Псевдоним: `task cms:up`. Остановка: `task docker:down` или `task cms:down`.
- Если используется чистый уже собранный image, `docker compose up --no-build -d --wait cms` обновляет контейнер без сборки из непроверенного рабочего дерева.
- Первый administrator создаётся отдельно; default account/password отсутствуют. Пароль вводит пользователь скрыто и передаёт через stdin.
- `docker compose run` не имеет флага `--no-build`; ранее такая ошибочная команда помешала созданию `owner`. Для account command используется `docker compose run --rm --no-deps -T cms admin-user ... --password-stdin` при остановленном CMS.
- Нативный запуск, backup/restore, SSH и отдельная static-публикация подробно описаны в [docs/cms.md](docs/cms.md) и [docs/deployment.md](docs/deployment.md).

Работающие backup-архивы содержат пользователей, сессии и SSH state. Они приватные. Restore выполняется в новый пустой том, исходный том сохраняется для отката.

### Ограничения и особые случаи

- Браузеры и браузерные сессии пользователь пока запретил. Скриншоты присылал пользователь; автоматического browser QA не было. После разрешения соблюдать предпочтение incognito.
- Ручной rebase не должен становиться публикацией из-за auto-publish policy.
- Неизвестный HEAD после возможного Git commit без receipt требует ручной проверки. Нельзя автоматически объявить этот commit своим или выполнить reset.
- История ограничена retention policy и не заменяет полный backup.
- Перемещение source и смена URL страницы не переписывают произвольные внешние ссылки.
- Предыдущий ресурсный замер reader относится к `2b42dd1`: 512 страниц, 68,4 MiB исходников, 2106 запросов, 1 CPU / 512 MiB, без ошибок/OOM/restarts. Это не замер итогового recovery-среза; полноценную нагрузочную приёмку повторить на этапе 7.

## C. Как продолжать после разрешения пользователя

Сначала прочитать CLAUDE.md, этот документ, действующие AGENTS.md, текущий Git status и актуальные CI/Taskfile-команды. Убедиться, какой commit действительно находится на origin и какой image запущен. Не считать чатовую память доказательством состояния диска.

### 2. Атомарная публикация нескольких существующих черновиков

Нужны серверная операция и выбор нескольких черновиков в Publishing. Для каждого сохраняются ID, собственная revision, автор и source base; весь набор проверяется до изменения файлов. Собирать один общий candidate, один сайт и одну транзакцию. Один запрещённый, устаревший или конфликтующий элемент отменяет весь набор. Удалять только успешно опубликованные точные версии выбранных черновиков. Проверить lost response/retry, права на объединение путей, отмену, историю и один связный Git commit без частичного успеха.

### 3. Импорт существующего Git из админки

Сейчас существующую историю можно использовать через подготовленный dedicated clone; UI enrollment локального проекта создаёт новую историю. Нужны изолированная подготовка clone, выбор branch, preview проекта и явное атомарное принятие. Не смешивать неродственные истории и не заменять активные данные до проверки. Ошибки сети, host key, manifest, ACL или build сохраняют текущий проект. Секреты должны оставаться на сервере.

### 4. Дополнительные providers

Разделить источник, чтение/запись, синхронизацию и публикацию по явным capabilities. Учитывать streaming, CAS, отмену, лимиты, историю и ветки там, где provider их поддерживает. Выбрать первый дополнительный provider осознанно; конкретный S3/WebDAV/cloud API ещё не обещан. Проверять отказ и восстановление на настоящей границе адаптера. Не превращать GET или сохранение настроек в неявную сетевую синхронизацию.

### 5. Планировщик

Добавить управляемое расписание, серверную identity с минимальными правами, lifecycle через Fx, single-flight, backoff и состояние последнего запуска. Незавершённая публикация блокирует конкурирующую синхронизацию. Поведение при выключении и retry проверять без flaky sleep. Автоматические действия должны быть явно включены настройкой.

### 6. Удобство CMS

Доработать связанный сценарий Documents/Files/Publishing, отображение своих и конфликтующих черновиков, сравнение, форматы, загрузки, перемещения, темы и настройки. Сохранить исходный текст, undo, selection и новые локальные изменения при асинхронных действиях. Доработать keyboard/focus/accessibility и понятные состояния ошибок. Безопасный HTML не должен становиться обходом ограничений scripts.

### 7. Нагрузка и отказоустойчивость

Повторить длительные проверки на последнем commit с ограниченными CPU/RAM. Проверить широкие и глубокие проекты, большие вложения, параллельных читателей/редакторов, отмену потоковых API-вызовов, bounded caches и shutdown. Добавить управляемые process-kill/FS/network сценарии на границах протоколов; подтвердить отсутствие утечек и сохранение источников после restart. Условия и commit каждого замера фиксировать явно.

### 8. Реальный browser QA

Начать только после разрешения. Проверить login/roles, редактор/preview/undo, сохранение свойств, Files, draft/publish/rebase, history/restore/delete plans, Git, темы, настройки и явные API-вызовы. Node DOM и HTTP-тесты не выдавать за проверку реального браузера.

### 9. Итоговая версия

Подготовить версию, changelog, инструкции миграции и восстановления, проверить чистый запуск CMS и отдельного static image, установить весь набор локальных release checks. Выпуск или deployment наружу требует соответствующей инструкции пользователя; локальный preview уже входит в текущую работу.
